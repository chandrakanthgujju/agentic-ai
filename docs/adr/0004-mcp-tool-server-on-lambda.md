# ADR-0004: Tools are an MCP server on Lambda behind an IAM-auth Function URL

- Status: Accepted
- Date: 2026-11-24

## Context

The agent needs "get info" style tools over a (mock) database plus knowledge-base search. In a real
company the tools are owned by different teams than the agent and change at a different pace. We
want to show tool governance: discovery, versioning, schemas, auth, timeouts and observability.

## Options

1. In-process Python functions registered with the agent. Simple, but couples tool releases to the
   agent, and there is no reusable contract other clients (IDEs, other agents) could consume.
2. Bedrock Agents action groups. Managed, but the orchestration loop is a black box and harder to test.
3. **An MCP (Model Context Protocol) server (chosen)**, deployed as its own Lambda/stack, consumed by
   the agent through the official `mcp` Python SDK.

## Decision

- `services/mcp_server` uses the official SDK (`mcp==2.3.0`), **stateless streamable HTTP with JSON
  responses**, which maps cleanly onto request/response Lambda (no sticky sessions needed).
- Hosted with Mangum on a module-level event loop so the SDK's session manager is started once per
  execution environment and reused across invocations.
- Exposed via a Lambda **Function URL with `AWS_IAM` auth**. Only the agent role is granted
  `lambda:InvokeFunctionUrl`; the agent signs every MCP HTTP request with SigV4 (`shared/sigv4.py`).
  DNS-rebinding protection in the SDK is disabled because it guards browser-reachable localhost
  servers; here IAM auth is the boundary.
- Tools: `get_customer_info`, `get_order_status`, `list_customer_orders`, `search_products`,
  `search_knowledge_base`. All are annotated read-only/idempotent, carry a catalog version in
  `_meta`, and validate input with typed signatures (JSON Schema generated by the SDK).
- The "database" is `MockCommerceRepository`: in-memory fixtures, a logged pseudo-SQL statement and
  simulated latency so the traces and logs look like a real DB call, but nothing is queried.
- The agent caches `tools/list` for 5 minutes, converts MCP schemas into Bedrock `toolSpec`s,
  runs tool calls from one model turn in parallel, enforces a 15 s per-call timeout, truncates large
  results, and keeps chatting without tools if the MCP server is down.

## Consequences

- Adding a tool is a change to one stack; the agent picks it up within the cache TTL.
- One extra network hop per tool call (~tens of ms warm, more on a cold start).
- Replacing the mock repository with a real one (RDS Data API, DynamoDB) touches only `mock_db.py`
  and the MCP function's IAM policy.
- Tool output is untrusted input to the model (prompt-injection surface); see `docs/security.md`.
